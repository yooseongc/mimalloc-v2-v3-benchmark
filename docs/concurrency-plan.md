# 동시 할당·해제에서 규모와 객체 크기의 영향

Design status: Frozen
Experiment: concurrency-v1
Date: 2026-09-22

질문: v3.5.3이 동시 작업에서 추가 메모리 사용에 상응하는 처리상의 이점을 주는가?
v2.1.2, v3.5.0, v3.5.3의 기본 정책을 비교한다. 특정 버전의 승리를 목표로 하지 않는다.
이전 순차 관찰의 코드와 결과는 변경하지 않으며 폐기된 옛 벤치마크는 사용하지 않는다.

## 흐름

할당자와 해제자 한 쌍마다 독립적인 단일 생산자/단일 소비자 원형 인계 공간을 둔다.
인계 단위는 256개 객체이며 슬롯 상태는 cache line 단위로 분리한다.
객체마다 queue CAS나 전역 통계를 갱신하지 않는다. 할당자가 전체 내용을 쓴 뒤
슬롯을 넘기면 해제자는 객체 식별값을 검증하고 해제한다. 빈 슬롯에 다시 할당한다.
서로 다른 슬롯에서 할당과 해제가 겹칠 수 있다. 슬롯을 기다리는 동안에는 CPU pause를
사용하고 일정 횟수마다 yield한다. 대기 반복 수는 worker의 지역 변수에 집계한다.

처음에는 전체 인계 공간을 채워 생존 요청량을 상한까지 올린다. 이후 고정된 객체 수를
처리하고 모두 해제한 뒤 worker가 살아 있는 상태로 5초 기다린다. 준비 할당은 처리
시간에서 제외하며 준비된 객체의 해제는 포함한다. 새로 할당한 개수와 전체 해제 개수를
별도로 기록하고, 처리량의 분자는 전체 해제 완료 객체 수다.

128 MiB는 정확히 유지되는 생존량이 아니라 **최대 생존 요청량**이다. 준비 단계에서는
이 상한에 도달한다. 작업 중에는 할당자와 해제자의 진행에 따라 변한다. 외부 관찰자는
처리 진행과 RSS를 함께 읽는다. 진행 카운터는 배치 경계에서만 공개하므로 생존량은
최대 몇 배치 수준의 오차와 읽기 시차가 있는 근사값이다. 정확한 시작·종료 객체 수를
별도로 검증한다. 이 프로그램은 실제 서비스의 요청 지연시간을 측정하지 않는다.

## 단계별 범위

1. 4 KiB, 128 MiB 상한에서 1쌍/2쌍을 먼저 관찰한다.
2. 같은 상한과 topology에서 64 B, 256 B, 1 KiB를 각각 관찰한다.
3. 4 KiB만 512 MiB 상한으로 확대해 큰 공간에서도 방향이 같은지 본다.

각 조건은 세 버전 × 3개 독립 프로세스다. 전체 기본 관찰은 90개다.
모든 조건을 한꺼번에 섞은 점수는 만들지 않고 질문별로 따로 설명한다.
각 반복에서 세 버전은 같은 객체 수를 처리하고 순서를 무작위화한다.
같은 객체 크기는 1쌍/2쌍과 공간 상한 간에도 총 처리 객체 수를 맞춘다.
준비 실행에서 더 빠른 조건도 대략 3초 이상 작업하도록 객체 수를 정한다.
정확한 수와 순서는 본 관찰 전에 동결한다. 3회는 패턴 탐색이며 동등성 검정이 아니다.

별도 retained 대조 실행은 처음 준비한 객체를 해제하지 않고 같은 쓰기·검증·인계만
반복한다. main 결과에서 이 시간을 빼지 않는다. retained에서는 생존 객체가 계속
유지되므로 작업 후 RSS를 기본 실행의 해제 후 RSS와 직접 비교하지 않는다.
이 대조 실행의 처리 속도가 main과 비슷하면 할당기 차이를 보기 어려운 조건으로 표시한다.

## 통제와 관찰

- 같은 Rocky 8 이미지, 기본 Release 라이브러리(새 memory-behavior 관찰에 사용한
  공식 source SHA와 라이브러리 SHA를 다시 검증), 같은 새 실행 바이너리를 쓴다.
- CPU는 A0/B2, 두 번째 쌍 A4/B6, 제어8, 외부 관찰10으로 고정한다.
  WSL2의 vCPU 배치이며 물리 호스트의 주파수·스케줄링은 통제하지 못한다.
- 실제 처리량·경과 시간, worker의 CLOCK_THREAD_CPUTIME_ID CPU 시간,
  할당자/해제자별 대기 횟수, RSS와 THP 관측, 시작·종료 생존량을 기록한다.
- 데이터 전체 쓰기는 실제 서비스 데이터 작업의 단순 모형이다. retained 대조군에도
  같은 작업을 둔다. 결과는 malloc/free 호출만의 속도가 아니다.
- RSS는 외부에서 약 100 ms 간격으로 읽고 경계에서는 smaps_rollup을 읽는다.
  샘플 최고 RSS와 프로세스 high-water mark는 구분한다. 관측 사이의 순간 peak는 모른다.
- 작은 smoke에서 전체 payload를 검증하고, 본 실행에서는 객체별 앞뒤의 64-bit
  식별값을 확인한다. 체크섬을 출력하고 예상 개수와 대조한다. Release 코드에
  전체 memset과 확인 코드가 남는지도 본다.
- 대조군, smoke, 준비 실행은 본 결과에 합치지 않는다. 실패는 원인과 기록을 남긴다.

예상 자원: 프로세스 하나씩, payload 상한 최대 512 MiB + 포인터·상태·allocator 공간.
기본 실행은 작업 3–수초와 idle 5초로 대략 10–20분, 준비와 대조군까지 약 30분을
예산으로 두며 준비 실행 후 갱신한다. host 설정은 바꾸지 않는다.

산출물은 조건별 처리 비용/처리량, 진행 중 메모리, 해제 후 메모리의 설명과 그래프다.
무엇이 커질 때 버전 차이가 벌어졌는지, 공간 효율과 처리 속도의 절충이 있는지,
인계나 데이터 쓰기 비용이 차이를 가렸는지를 구분한다.

## 유효성 및 해석 제한

라이브러리·바이너리 hash, 버전·주입 경로, worker CPU 배치, 객체 수·내용 체크섬,
종료 생존량, 정상 종료를 확인한다. swap 발생이나 cgroup CPU throttling 증가는
실패로 보존하며 실행을 중단한다. 오류를 성공 결과로 교체하지 않는다.
준비 실행은 크기·쌍·버전별 1회이며 성능 판정에 사용하지 않는다.
초기 검증의 1 MiB 설정은 4 KiB/2쌍에서 최소 두 배치 공간보다 작아 입력 검증이
거부했다. 기록을 보존하고 2 MiB로 고친 전체 24개 검증이 통과했다.

1쌍에서 2쌍으로 바꿀 때 전체 공간 상한은 같고 각 쌍의 공간은 절반이다.
따라서 스레드 수만 바꾸는 실험이 아닌 고정 총량에서의 병렬화 비교다.
독립적인 인계 공간 두 개이며 하나의 다중 생산자 queue 경합을 재현하지 않는다.
대기 중 CPU 소비도 worker CPU에 포함한다. 대기 횟수는 시간이나 비율이 아니다.
이 실험에는 실제 요청 지연시간, perf hardware counters, 다중 NUMA 관찰이 없다.
초기 전체 공간 채우기가 공통 준비 과정이며 별도 malloc/free warm-up은 하지 않는다.
실제 큰 객체의 전체 쓰기 비용이 지배하면 allocator 고유 호출 비용으로 일반화하지 않는다.
