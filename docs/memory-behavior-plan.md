# 처리 비용과 메모리 흐름을 이해하기 위한 새 계획

Design status: Frozen
Design revision: memory-behavior-v1
Execution status: Complete (18 baseline flows + 6 separate collection probes)
작성일: 2026-09-21

사용자는 버전별 처리 비용·메모리 사용 및 반환 패턴과, 다른 스레드에서
해제할 때의 변화를 함께 알고 싶다고 답했다. 이 두 질문이 계획의 기준이다.
이전 계획·하네스·측정 결과·성능 결론은 모두 이번 판단의 근거에서 폐기한다.
기존 횟수나 시나리오를 승계하지 않는다. 사용자의 후속 실행 지시로 구현과 관찰을 완료했다. 결과는 memory-behavior-report.md에 있다.

## 1. 무엇을 설명할 것인가

최종 설명은 다음 문장을 실제 관찰로 채울 수 있어야 한다.

> 같은 양의 데이터를 다룰 때 버전 A는 B보다 어느 단계에서 시간을 더 쓰고,
> 메모리를 얼마나 보유하며, 다른 스레드에서 해제하면 이 흐름이 어떻게 바뀐다.
> 남은 메모리는 다음 작업에 재사용되는지, 반환시키면 어떤 비용이 생기는지 확인했다.

| 사용자 질문 | 비교할 장면 | 답을 판단할 자료 |
|---|---|---|
| 평소 처리 비용과 메모리 사용은 어떻게 다른가? | 같은 크기·개수의 객체를 할당하고 같은 범위에 값을 씀 | 할당·쓰기·해제의 단계별 시간과 CPU 시간, 생존 객체 바이트, RSS |
| free했는데 메모리가 남는가? | 일부 해제 → 전부 해제 → 아무 일도 하지 않음 | 생존 객체 바이트가 줄 때 RSS가 함께 줄어드는지, 시간에 따른 변화 |
| 다른 스레드에서 free하면 무엇이 달라지는가? | A가 할당·해제 / A가 할당하고 B가 해제 | 해제 스레드 비용, 해제 후 RSS, A의 다음 할당 비용 |
| 남겨둔 메모리는 다음 작업에 도움이 되는가? | 동일한 크기·개수로 다시 할당하고 씀 | 첫 작업 대비 재할당·쓰기 시간, 페이지 폴트, RSS 추가 증가 |

RSS가 줄지 않았다는 관찰만으로 누수라고 부르지 않는다. RSS와 생존 객체
바이트의 차이만으로 단편화 크기라고 부르지도 않는다. 하네스 자체의 메모리,
allocator 관리 공간, 아직 반환하지 않은 페이지 등은 별도 설명이 필요하다.

## 2. 먼저 볼 하나의 흐름

첫 장면은 수명과 크기가 명확한 객체 집합이다. 실제 애플리케이션의
큐·TCP·서비스 단계를 가정하지 않는다. 실제 사용 패턴은 아직 제공되지 않았다.

1. **준비:** A와 B 스레드를 만들고 계속 살려 둔다. 포인터 목록과 관찰용
   버퍼를 미리 준비한다. 작은 정해진 준비 작업을 두 조건에 동일하게 적용하고
   그 후 기준 RSS를 기록한다. 프로세스 시작 이후 경과도 따로 남긴다.
2. **할당:** A가 같은 크기의 객체를 정해진 개수만큼 할당한다.
3. **사용:** A가 모든 객체에 같은 범위의 값을 쓴다. 할당 시간과 쓰기 시간을
   분리하면서 두 단계의 합도 함께 제시한다. 할당 시점의 페이지 처리 비용이
   쓰기 시점으로 이동한 것을 성능 개선으로 오해하지 않기 위해서다.
4. **일부 해제:** 인덱스가 짝수인 객체 50%를 해제한다. 나머지 객체는 유지한다.
   같은 객체들이 두 비교 조건에서 생존하도록 하고, 생존량과 RSS를 기록한다.
5. **전부 해제:** 나머지를 해제한다. 생존 객체 수가 0인지 검증한다.
6. **휴식:** A와 B를 모두 살려 둔 채 allocator 호출 없이 30초 기다린다.
   해제 직후와 10 ms, 100 ms, 1초, 5초, 30초 부근의 실제 관찰 시각과 RSS를 남긴다.
   목표 시각을 놓치면 실제 시각을 그대로 표기한다.
7. **재사용:** A가 처음과 같은 객체 집합을 다시 할당하고 쓴다.
   재할당·쓰기 비용, 페이지 폴트, RSS 증가를 기록하고 마지막에 모두 해제한다.

이 흐름을 다음 두 조건에서만 바꿔 실행한다.

| 조건 | 최초 할당·쓰기 | 일부·전체 해제 | 재할당·쓰기 |
|---|---|---|---|
| 동일 스레드 | A | A | A |
| 다른 스레드 | A | B | A |

두 조건 모두 A와 B를 생성하고 동일한 CPU 위치와 동기화 절차를 사용한다.
객체 목록은 일괄 인계하며 객체마다 큐에 넣지 않는다. 각 단계의 작업 시작부터
완료까지를 재고, 인계·대기 시간은 별도로 남긴다. 동시에 할당과 해제를 진행하는
상황은 이 첫 실험의 범위가 아니다. 따라서 이 결과를 실제 파이프라인 처리량으로
일반화하지 않는다.

**핵심은 free 호출이 끝나는 시점에서 관찰을 끝내지 않는 것이다.**
B의 해제가 빨라도 A가 다시 일을 시작할 때 비용이 늘 수 있으므로 둘을 함께 본다.

## 3. 첫 실행 범위와 다음 질문

첫 설정의 초안은 객체당 4 KiB, 총 요청량 128 MiB(32,768개)다.
성능을 잘 보이게 하려는 크기가 아니라 생존량과 단계별 RSS를 쉽게 설명할 수 있는
출발점이다. 실제 사용 사례의 대표 크기가 확인되면 실행 전 이를 바꾼다.
메모리 여유와 계측 해상도는 준비 실행에서 확인한다.

주 비교는 v3.5.0 ↔ v3.5.3이며, v2.1.2도 같은 흐름을 실행해 기준으로 표시한다.
세 버전 × 두 해제 조건 × 세 독립 프로세스, 총 18개 흐름부터 관찰한다.
버전·조건 실행 순서를 섞고 원래 순서를 기록한다. 한 프로세스 안의 여러 구간을
독립 반복으로 세지 않는다. **3회는 패턴을 찾는 탐색이며 성능 우열을 확정하는 표본이 아니다.**

처음부터 크기·스레드·정책의 모든 조합을 실행하지 않는다. 관찰에 따라 다음 질문을 선택한다.

| 첫 관찰 또는 미해결 질문 | 다음에 한 가지 바꿀 것 | 확인하려는 이유 |
|---|---|---|
| 다른 스레드에서 해제한 뒤 A의 재시작이 다름 | 해제 후 A가 고정량의 작은 할당·해제를 수행하는 조건 추가 | 할당한 스레드의 후속 활동과 비용·RSS 변화의 관계 |
| 아무 작업 없이 기다릴 때 RSS가 남음 | 기본 동작과 명시적 collect를 별도 실행으로 비교 | 반환 가능한지와 반환·다음 재사용 비용을 함께 확인 |
| 한 번의 burst로 지속 사용이 설명되지 않음 | 동시에 살아 있는 객체 양을 고정하고 일부를 교체하는 흐름 | 장기 반복 시 비용·RSS가 안정되는지, 계속 증가하는지 |
| 4 KiB만으로 크기의 영향이 설명되지 않음 | 256 B와 64 KiB를 각각 별도 장면으로 추가 | 요청 바이트를 같게 했을 때 객체 수 차이를 포함한 행동 변화 |
| 일부가 오래 살아 있을 때가 궁금함 | 같은 최대 생존량에서 해제 인덱스·잔존 비율만 변경 | 잔존 객체 배치가 메모리 유지·재사용에 주는 영향 |
| 스레드 종료가 관련될 때 | A가 생존하는 조건과 종료하는 조건을 분리 | 스레드 생명주기가 해제 이후 흐름에 주는 영향 |

한 후속 관찰에서 여러 원인을 동시에 바꾸지 않는다. 30초 이후에도 반환되지 않을
가능성을 이 초안에서 결론내리지 않는다. 필요하면 관찰 시간을 늘리는 별도 질문을 둔다.
후속 정책의 지원 여부와 의미는 각 tag 소스에서 확인한 뒤 실행 조건에 기록한다.

## 4. 무엇을 만들고 무엇을 측정할 것인가

기존 하네스를 고쳐 쓰지 않고 위 흐름만 수행하는 작은 관찰 프로그램을 새로 만든다.
기존 실행기·분석기의 import나 기존 raw 결과 로딩도 사용하지 않는다.
공식 source SHA는 출처 식별에만 재사용할 수 있으며, 빌드와 환경은 새로 검증한다.

- **시간:** 할당, 쓰기, 일부 해제, 나머지 해제, 재할당, 재쓰기 각각의 벽시계 시간.
  해제 작업을 수행한 worker의 CPU 시간도 기록한다. 단계 시간은 호출 한 번의
  지연시간이나 p99라고 이름 붙이지 않는다. 초기 실험에는 호출별 timestamp를 넣지 않는다.
- **메모리:** 요청한 생존 바이트·객체 수와 프로세스 RSS의 시간 흐름을 함께 그린다.
  기준 RSS도 보여 주며 기준을 뺀 값만 제시하지 않는다. 프로세스 high-water mark는
  전체 실행의 값으로 표시하고, 샘플 중 최댓값과 구분한다.
- **보조 근거:** 단계 경계의 minor/major fault, 환경이 제공하는 swap 상태.
  원인 설명이 더 필요할 때만 별도 진단에서 PSS/AnonHugePages/allocator 통계를 확인한다.

생존량은 프로그램이 이미 아는 객체 수와 크기로 계산한다. RSS 관찰은 별도 관찰자가
수행하고, 작업 worker는 측정 중 로그 파일을 쓰거나 결과 벡터를 확장하지 않는다.
빠른 단계는 RSS 샘플 사이에서 끝날 수 있으므로 경계 관찰과 전체 high-water mark를
보완해서 쓰되 관측하지 못한 순간별 peak를 만들어내지 않는다.

## 5. 관찰 도구가 질문을 가리지 않게 할 최소 검증

검증의 목적은 실행 건수를 늘리는 것이 아니라 숫자가 무엇을 뜻하는지 확인하는 것이다.

1. 실제 라이브러리·버전과 같은 실행 바이너리를 확인한다. 세 버전은 같은 Rocky 8
   이미지, compiler, 공통 Release 설정, CPU 배치와 메모리 조건에서 비교한다.
   최초 비교는 각 버전의 기본 정책이다. 버전 기본값의 효과가 포함됨을 명시한다.
2. 모든 객체가 지정한 스레드에서 정확히 한 번 해제되는지, 살아 있는 객체의 데이터가
   유지되는지 검증한다. 쓰기·읽기 결과는 측정 후 출력·검증되는 값에 연결하고
   Release 바이너리에도 의도한 작업이 남는지 확인한다.
3. 빈 단계의 인계·시계 조회 비용과 관찰자 유무의 영향을 준비 실행에서 확인한다.
   짧은 단계가 계측 비용과 비슷하면 우열을 발표하지 않는다. 정확한 시간 측정이
   필요할 때만 별도 반복 구간을 설계하며, 메모리 관찰의 객체 수를 몰래 늘리지 않는다.
4. A와 B를 같은 NUMA node의 서로 다른 CPU에 배치하고 두 조건에서 위치를 유지한다.
   WSL2라면 vCPU 배치와 물리 CPU 통제를 구분한다. host 부하나 swap 때문에
   설명이 어려운 실행은 이유와 원자료를 함께 남긴다.

모든 상세 환경 필드를 먼저 모으느라 관찰 프로그램을 거대하게 만들지 않는다.
해석에 필요한 환경과 실제 변경한 변수는 빠짐없이 기록한다. 새 실행 시점의 자원과
이미지 식별값은 다시 확인하며 이전 실험 상태를 현재 사실로 가정하지 않는다.

## 6. 결과를 이해하는 방법과 완료 기준

첫 산출물은 종합 순위표가 아니라 **시간에 따른 생존량·RSS 그래프와 단계별 비용 표**다.
같은 스레드/다른 스레드를 나란히 놓고 세 버전의 각 반복도 볼 수 있게 한다.
“A가 더 빠르다” 대신 “이 단계에서 이만큼 시간이 들고, 해제 후 이만큼 남으며,
재사용 때 이런 비용이 나타났다”라고 설명한다. 관찰과 원인 추정은 구분한다.

설명되지 않는 변화가 있으면 해당 단계 하나를 추가 관찰한다. 단순 반복 증가로
문제를 덮지 않는다. 미세한 버전 차이를 확정할 필요가 생기면 그때 별도 확인 실험의
대표 지표·실용적인 차이 기준·반복 수를 결과 수집 전에 정한다. 기존 15/30회 규칙을
자동 적용하거나, 유리한 결과가 나올 때까지 반복하지 않는다.

다음 네 질문에 관찰 근거로 답하면 첫 조사를 마친다.

- 동일 작업에서 시간이 어디에 쓰이고, 생존량과 RSS가 어떻게 움직이는가?
- 해제 스레드만 바꾸었을 때 그 흐름의 어느 부분이 달라지는가?
- 해제 후 남는 메모리와 다음 작업의 비용 사이에 어떤 관계가 관찰되는가?
- 버전 간 차이라고 확인한 것, 관찰했지만 원인이 불명확한 것, 아직 확인하지 않은 것은 무엇인가?

세 탐색 반복으로 작은 성능 차이를 확정하지 못해도 관찰 범위를 정직하게 설명할 수 있으면
의미 있는 결과다. “유의하지 않으므로 같다”는 결론은 사용하지 않는다.

## 7. 실행 순서와 규모

1. 이 계획을 기준으로 작은 프로그램과 외부 관찰자를 새로 구현한다.
2. 한 버전·두 해제 조건의 작은 객체 집합으로 데이터 생명주기와 계측을 점검한다.
3. 메모리 크기·시간 해상도·관찰자 영향을 확인한 뒤 첫 관찰 설정과 순서를 동결한다.
4. 첫 18개 흐름을 실행하고 그래프를 보며 네 질문에 답한다.
5. 답하지 못한 질문에 한해서 위 후속 관찰을 선택하고 별도 설정으로 기록한다.

첫 관찰의 idle만 합하면 9분이다(18 × 30초). 작업·준비·검증을 포함한 실행 예산은
대략 15–30분으로 잡되 실제 시간은 준비 실행 후 갱신한다. 구현 시간은 포함하지 않는다.
프로세스는 한 번에 하나만 실행하며 첫 요청량은 128 MiB, 실제 RSS와 관찰 버퍼의 여유를
확인한다. 그 이상 규모 확대는 이 계획의 자동 실행 범위에 넣지 않는다.

실제 객체 크기·수명·동시 보유량·할당/해제 스레드 수가 제공되면 대표 흐름을 조정한다.
현재 초안은 특정 애플리케이션을 재현한다고 주장하지 않는다.

## 실행 전 확정 사항 (사용자의 실행 지시 후)

Frozen at: 2026-09-21T12:43:12.084104+00:00

위 초안의 계획 단계는 종료했고 새 구현·실행이 승인되었다. 본 관찰은
4 KiB × 32,768개, 30초 idle, 3버전 × 2조건 × 3회로 확정했다.
두 worker가 각각 32개를 같은 스레드에서 할당·전체 쓰기·해제하며 준비한다.
A=CPU 0, B=CPU 2, 제어 스레드=CPU 4, 외부 관찰자=CPU 6이다.
데이터 쓰기는 객체 전체 memset이며, 별도 단계에서 모든 생존 바이트를 검증한다.
검증은 작업 시간에서 제외하지만 뒤따르는 작업의 cache 상태에 영향을 줄 수 있다.
포인터 목록은 별도 mmap 공간에 두고 baseline에 포함한다.

작업이 짧아 본 관찰에서는 주기적 RSS 조회를 끄고, 단계가 끝나 멈춰 있는
시점에 외부에서 smaps_rollup을 읽는다. idle은 정해진 시점에만 읽는다.
이는 주기적 감시의 영향이 없다고 입증했다는 뜻이 아니다. 준비 실행의
감시 on/off 각 1회로 작은 계측 영향과 환경 변동을 분리할 수 없었으므로
측정 중 관찰을 줄인 선택이다. 단계 경계의 관찰·검증 대기는 그래프의 실제 시각에 포함된다.

빈 작업 구간과 전체 payload 검증, 잘못된 해제·종료 거부를 확인했다.
의도된 오류 종료 테스트는 최초 5초 제한을 넘겼고, 검증용 제한을 20초로
늘려 기대한 오류 종료를 확인했다. 정상 smoke 6개·준비 실행 12개는 모두 통과했다.
실제 Release 바이너리의 malloc/free/memset 호출과 payload 검증 루프도 확인했다.
기존 하네스나 결과는 사용하지 않았다.

새 source/runner/artifact 해시와 실행 순서는 experiments/memory-behavior-v1/plan.json에 고정했다.
3회는 탐색 관찰이며 작은 성능 차이를 확정하는 통계 검정으로 사용하지 않는다.
