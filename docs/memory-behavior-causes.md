# 관찰한 차이의 원인 확인 (2026-09-22)

## 메모리 증가: 페이지당 수용량 감소를 직접 확인

새 구조 진단 `observation/page_layout.cpp`로 실제 측정에 사용한 두 라이브러리를
각각 열었다. 별도 heap에 4 KiB 객체 256개를 할당한 뒤 공식 heap visitor API로
영역 정보를 읽었다. 성능 측정이 아니며, 기존 바이너리·라이브러리·원자료는 변경하지 않았다.

| 항목 | v3.5.0 | v3.5.3 |
|---|---:|---:|
| 내부 small page 크기 | 64 KiB | 64 KiB |
| 객체 영역의 페이지 시작점 대비 오프셋 | 0 | 4 KiB |
| 객체를 넣을 수 있는 영역 | 64 KiB | 60 KiB |
| 한 페이지의 4 KiB 객체 수용량 | 16 | 15 |
| 256개 객체를 담은 영역 수 | 16 | 18 |

진단 결과: [v3.5.0](../experiments/memory-behavior-v1/layout-v350.json),
[v3.5.3](../experiments/memory-behavior-v1/layout-v353.json).

v3.5.3의 `include/mimalloc/types.h`는 이 빌드에서
`MI_PAGE_META_SMALL_IS_ALIGNED`를 활성화한다. `src/arena.c`의
`mi_arenas_page_alloc_fresh`는 small page 앞에 관리 정보를 배치하고,
`mi_page_block_start`는 4 KiB 객체의 시작점을 4 KiB로 정렬한다.
관리 정보 자체가 4 KiB라는 뜻은 아니다. 관리 정보와 정렬 여백 때문에
첫 객체가 4 KiB 뒤에서 시작한다.

반면 v3.5.0의 해당 경로는 이 객체 크기에서 관리 정보를 별도 영역에 두고
객체 시작 오프셋을 0으로 둔다. 이 차이는 전용 small-free API를 직접 사용하지
않아도 일반적인 4 KiB 할당의 메모리 배치에 영향을 준다.

가득 찬 페이지 기준 같은 수의 객체를 담는 데 필요한 공간 비율은 16/15,
약 6.7% 증가다. 원래 관찰의 32,768개에 적용한 **페이지 수용량 계산**은
2,048페이지(128 MiB) 대 2,185페이지(약 136.56 MiB)다. 이는 RSS를 직접
계산한 값이 아니다. THP의 2 MiB 단위와 다른 메타데이터·기준 RSS가 별도로 있다.
실제로 관찰한 THP 130 → 140 MiB 및 RSS 약 10 MiB 증가와 규모가 맞는다.

따라서 메모리 차이를 단순히 “THP 기본값이 바뀌었기 때문”이라고만 설명하는
것은 부족하다. **페이지 내부의 객체 밀도 감소를 직접 확인했고, THP 단위가
실제 상주 메모리 크기에 함께 반영됐다**고 설명하는 것이 더 정확하다.
코드 주석은 이 배치가 빠른 페이지 정보 조회와 small-free 경로를 위한 것임을
설명하지만, 이번 관찰에서 속도상의 보상이 확인됐다는 뜻은 아니다.

## free가 반환·재사용과 다른 이유: 코드 경로 확인

v3.5.3 `include/mimalloc/types.h`의 page 설명에는 서로 다른 free 목록이 있다.
현재 할당 가능한 목록, 같은 스레드가 해제한 목록, 다른 스레드가 해제한 목록이다.
`src/free.c`의 local free는 목록과 사용 개수를 갱신하고, 다른 스레드 free는
atomic 연산으로 별도 목록에 연결한다. 객체 하나를 free하는 것은 매번 해당
물리 메모리를 OS에 반환하는 동작이 아니다.

`src/arena.c:mi_arena_schedule_purge`는 지연 반환을 즉시 실행하는 대신
시각과 대상 범위를 기록할 수 있다. 수집 경로에서는 실제 purge를 실행한다.
따라서 두 worker를 멈춘 채 기다리는 것과 owner가 `mi_collect(true)`를
실행하는 것은 다르며, idle 30초와 명시적 수집의 서로 다른 관찰을 설명한다.
명시적 반환 후에는 다음 할당에서 페이지를 다시 확보·준비해야 하므로
RSS 절감과 다음 사용 비용 증가가 함께 나타날 수 있다. 단일 수집 진단으로
그 비용의 정확한 분해나 비율을 확정하지는 않았다.

## 해제 시간 증가의 정확한 원인은 아직 확정하지 않음

free의 사용 개수 표현, 페이지 조회 및 소유권 처리, 통계 처리와 페이지 배치가
함께 바뀌었다. 실제 Release 빌드에서 v3.5.3은 MI_STATS=1, MI_PROFILE=1,
MI_DEFAULT_ALLOW_THP=2를 사용한다. 그러나 통계는 일부 slow path로 묶어
처리하도록 구현되어 있어 “통계가 켜져서 느려졌다”라고 단정할 수 없다.
secure/debug 전용 검사도 이번 빌드의 실행 비용이라고 가정하면 안 된다.

페이지 수 증가가 페이지 관련 처리량을 늘리는 요인이 될 수는 있지만,
이번 same/remote 해제 시간 차이 전체를 설명한다고 검증한 것은 아니다.
특정 변경이 원인인지 확정하려면 해당 변경만 달리한 별도 진단이 필요하다.
현재 확정할 수 있는 것은 해제 시간의 관찰값과 메모리 배치 차이이며,
해제 시간 증가를 특정 커밋에 귀속하는 것은 미확인이다.
